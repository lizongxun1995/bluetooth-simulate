# 歌词来源调研 SOP(Phase 0)

目的:搞清楚"车机上的歌词到底从哪来",直接决定 Phase 3(歌词推送)能否实现和怎么实现。
预期 1~2 天,可用任意一台真手机 + 一台目标车机完成。

## 步骤一:对照实验(10 分钟)

1. 手机播放**本地音乐文件**(自造的歌名,如"XKZZ-测试曲001",车机歌词库不可能有),
   手机开飞行模式(断网)。
2. 连接车机播放,观察车机:
   - **仍显示歌词** → 歌词在车机本地/由车机联网匹配(不太可能,因为它匹配不到自造歌名),
     或歌词藏于元数据;
   - **不显示歌词** → 歌词来自手机推送(或车机对真实歌名联网拉取)。继续步骤二。

## 步骤二:抓真手机蓝牙包(关键)

1. 手机:开发者选项 → 开启**"蓝牙 HCI 信息收集日志"**(各厂商入口略有差异)。
2. 手机正常联网,连车机播放**带歌词的在线歌曲**(记下歌名与歌词第一句)。
3. 播放至少 1 分钟(覆盖多次歌词滚动),停止播放,断开连接。
4. 导出日志:`/data/misc/bluetooth/logs/btsnoop_hci.log`(部分机型在
   `SDCARD/MIUI/debug_log`、`/sdcard/btsnoop_hci.log` 等,或在 bugreport 里)。
5. 用本工具分析:

```
python tools/btsnoop_avrcp.py btsnoop_hci.log
```

工具会列出手机→车机方向上的:
- AVRCP vendor-dependent 载荷(私有歌词协议最常见位置);
- RFCOMM/未知 L2CAP 通道载荷(自定义协议嫌疑)。

## 步骤三:结论分流

| 观察结果 | 结论 | Phase 3 动作 |
|---|---|---|
| 通道干净,车机联网可见 | 车机自己拉歌词 | **无需实现**,保证 AVRCP 元数据准确即可 |
| AVRCP vendor PDU 里出现歌词文本/时间戳 | 私有 AVRCP 扩展 | 按 HEX 分析 PDU 结构 → 固件 vendor 钩子实现 `lyrics.push` |
| 未知 L2CAP/RFCOMM 通道有大量带时间戳文本 | 自定义通道 | 分析帧格式,评估固件实现(该通道通常随 SPP 类协议,实现难度中) |
| 全都没有但车机显示歌词 | 歌词来自车机本地曲库 | 同第 1 行 |

## 注意

- 部分手机需 root 才能拿到 btsnoop 日志;不行就换 Pixel/小米的开发者日志入口试,
  或用蓝牙抓包硬件(如 Ellisys/CSR sniff,实验室若有)。
- 若第 1、2 步都需要,把抓包结果(尤其 vendor/未知通道的 HEX 片段)留存归档,
  作为 Phase 3 的输入与验收对照。
